# Native outcome journal implementation review

Read-only review of the uncommitted journal core on October 20. **The page storage is crash-shaped and rejects the tested duplicate conflicts, but three boundaries need repair before calling it bounded or erased.** I did not run tests; the parent reports 52 focused Swift and 43 Android passes. The collector, ACK, export and success pruning cutovers remain gated, as do the whole-partition Saved cache and old-install migration.

## Findings

1. **P1 — routine page reads grow with the entire manifest.** Swift `GuestDataStore.verifyOutcomeRows` runs six whole-collection `fetchCount` queries on every `collectOutcomeStep`, replay and evidence page. Android `LibraryOutcomeJournal.verifyRows` performs `GROUP BY` over every stored member on each reopen, replay and evidence page. Page *writes* stay at 50 rows, but a manifest of N members makes collection and export O(N²/50) scanned rows. This defeats the per-call bound at large folder sizes. The parent is already preparing a fix: validate the current 50-row page and durable checkpoint incrementally; perform a full consistency pass only at terminal readiness/reopening an already complete proof. Export should verify contiguous bounded pages as it streams. On iOS the current `FetchDescriptor` sorting by `ordinal` also needs an indexed, collection-scoped range; a fixed-width ordinal key gives a direct bounded lookup.

2. **P1 — erasure leaves private scope metadata, and Android can recreate it after erasure.** Swift `eraseOutcomeEvidence` rotates `GuestOutcomeScope.generation` and removes members/headers but never removes scope rows containing subject, namespace and owner. Android `LibraryOutcomeJournal.erase` likewise updates `scopes.generation` and deletes headers, leaving the subject/owner row. An absent scope is itself a valid old-generation fence, so delete the scope after facts/headers are gone (or retain only a documented non-identifying erasure tombstone). More immediately, Android `GuestStore.collectOutcomeStep` calls `captureGeneration` **before** `assertOutcomeOwnerActive`; a stale call after deletion can insert a new scope row and then fail the owner check. Validate owner/deletion phase and capture/open under the same store mutex before fetch, then revalidate owner and captured generation after fetch. Test stale calls after account deletion, not just a late response during partition recreation.

3. **P2 — erasure work and retry order differ across platforms.** Android `erase` deletes all matching headers in one SQLite transaction; the foreign-key cascade can delete an arbitrary number of member rows in that same call. Use an indexed bounded member/header sweep with a durable erasure fence if arbitrary folder sizes are in scope. Swift account deletion now erases journal evidence before moving its deletion phase to `identityPending`, so a crash mid-sweep can retry. Swift `eraseSyncPartition` still commits partition deletion *before* journal erasure; a crash in between leaves orphan journal rows with no deletion intent to resume. Reverse that order or give this API a durable erase intent. The new tests cover completed erasure and stale in-flight pages, but not interruption between these commits or a restarted multi-page sweep.

4. **P2 — duplicate terminal variants are not consistently classified.** After a page has advanced the checkpoint, both `persistOutcomePage` and Android `persist` accept a replayed `unavailable` response at an older ordinal with no row comparison and return the existing checkpoint; a same-start duplicate `unavailable` after an unavailable terminal instead throws. Neither path corrupts rows or creates ACK now, but the journal should define exact duplicate-versus-conflict behavior for terminal unavailability, especially when later settlement consumes its status. Keep `proof_unavailable` distinct from `detail_unavailable`; neither is a complete member set.

## What the current tests do establish

Both platforms use an owner/subject/namespace/receipt-bound key, enforce 50 rows and 64 KiB at the native boundary, compare exact ordinal/category counts, keep per-page rows outside the large partition JSON, and leave that partition unchanged while collecting. Swift uses a fresh context per page and saves rows plus checkpoint together; Android uses SQLite primary/unique keys and one transaction for rows plus checkpoint. The reopened-store duplicate tests exercise conflicting evidence rather than merely calling a pure validator. SwiftData's unique attributes can upsert on collision, so its explicit fetch-and-compare is essential; keep a reopened-context test when changing row keys. These local fixtures use synthetic server pages and do not prove the live page producer, account transition, or two-device delivery.

Before any ACK integration, bind the journal header to the exact local frozen operation/intent digest as well as the committed receipt, preserve available original intent for unavailable/partial results, and keep the existing manifest ACK guard until a durable terminal collection or explicit recoverable-unavailable decision has been recorded. A complete journal is evidence storage; it is not yet a successful sync receipt.
