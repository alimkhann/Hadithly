## Findings

### P2: head recreation can reattach orphan children and reset the serial

Both beginSavedViewRows implementations return an existing validated head or insert serial0 after checking the three-head cap. The absent-head path does not check for retained rows/indexes under the same view identity. If only a head disappears, begin with the same identity silently recreates serial0 over older child data. An old serial0 ticket can become valid again even though the retained children came from later writes. This is an ABA failure of the advertised serial-bound draft ticket, independently of any future publication/completeness claim.

Ordinary writes atomically save head/rows/indexes, so a headless child set is not a normal interrupted batch to resume by resetting its serial. Reject it fail-closed and preserve it for retained export/erasure, as existing private Saved assembly creation already does for its orphan children. Before inserting a new head, use bounded indexed key-prefix existence probes for saved_view_rows and saved_view_indexes. Add a real-disk regression: create serial0 ticket, write a row, delete only head via fixture, then begin the same identity must reject instead of reviving the old stamp. Scope erasure/recreated owner should remain protected by the existing private epoch guard.

### P2: accepted terminal serial creates an unreadable returned stamp

Both viewHead implementations accept serial strictly below9007199254740990. writeSavedViewRows then increments without checking the resulting serial. A valid old serial9007199254740989 can therefore commit rows/indexes/clock and return serial9007199254740990, which every later viewHead rejects. A successful write has produced an unusable next stamp.

Validate next serial before mutating/saving, or define a readable terminal serial with further writes rejected. Keep the same bound on both platforms. A real-store boundary fixture should capture rows/indexes/export fence, attempt the exhausted write and prove full rollback rather than an unusable accepted commit. This is separate from the already implemented export-clock overflow guard.

### P2: Android export/scalar decoding can coerce malformed stored metadata

viewHead correctly checks Cursor FIELD_TYPE_INTEGER for serial, but savedExportRecords section4 only calls getLong plus a range check. SQLite serial=0.5 can thus be exported as0 while ordinary head reading rejects that same row. viewRow and section5 similarly narrow kind with getInt, so a noninteger or oversized value can coerce to item1/folder0. The fingerprint covers the JSON payload, not these scalar metadata fields.

Require actual integer storage type and read Long before accepting exact kind0/1 and serial range. Apply consistently to draft reads and retained export. The scoped private evidence export should reject malformed metadata rather than emit a converted value. iOS's typed model properties do not have this Cursor conversion seam.

## Storage boundary checks that look sound

- Schema v7 is additive. Fresh create gains three draft-view tables; old v1-v6 branches preserve their prior Saved/local-state tables and add current view tables. SwiftData adds three models. Exact installed/predecessor upgrade runtime evidence must still be recorded separately from source inspection.
- Heads bind full owner, private scope epoch and draft generation. Head reads re-admit current account/deletion and validate identity metadata; production data cannot become readable through a foreign owner or stale private epoch. At most three heads per owner scope are admitted. This cap is a storage bound; retiring/reclaiming unused heads is future orchestration work.
- Android write/head/index/serial/export-clock changes run in one SQLite transaction. Swift batches use one fresh autosave-disabled context and rollback escaping mutation/save errors. No network await is held inside either write. Android clones rely on DB serialization; iOS synchronous MainActor writers are in-process serialized, not a proven multi-process protocol.
- A batch accepts one through eight logical private rows. Item values have a bounded private payload; each visible item contributes at most sixteen facet/folder/route keys. The technical write count is larger than eight, explicitly and finitely bounded. Do not label eight logical rows as eight total SQL operations.
- Exact target reads do not search a loaded window. Query scans use an indexed closed key prefix with LIMIT(pageSize+1), at most33 heads plus exact target reads; no broad all-library postfilter/anti-join is introduced. Every returned value validates owner/view metadata, key-to-identity, fingerprint, rank and selected scope. Selection validation is explicit.
- Tickets bind identity, serial and selection/name. A committed write invalidates old tickets. Unresolved collection coverage probes a dedicated materialized scope, preserving private rows whose public route is unknown. These are draft results; they do not certify that the entire input generation has been compiled or every index exists.
- iOS account admission now uses exact metadata fetchCount rather than materializing account stateData, so bounded draft reads avoid the large account queue blob. The fresh row context is still the one used for subsequent view operations.

## Privacy, export and cleanup

New persisted rows contain SavedPrivateItem, collection classification and deletion provenance, without full public passages. Existing localSavedEvidence sections4/5 stream private view heads and rows by subject/deployment key range in groups of eight, including retained old-owner/headless evidence. Derived technical indexes are not duplicated into consumer export. Export checks exact scope/key/fingerprint and the existing shared mutation fence; draft writes bump that fence in the same commit.

Presence probes, erasure and final scope-empty checks now include heads, private rows and indexes. Index cleanup uses128 small technical records per step, matching max16 keys ×8 logical records; private rows/heads retain the eight-record budget. Old Saved collection/fact budgets are unchanged. Full owner/subject/deployment erasure retains its fence and sibling protection. These source changes account for extra retained copies rather than hiding the new derived private state outside export/delete.

The component exposes draftSavedViewItem/Page/Folder/FolderPage, not a published complete view handle. Raw arbitrary batches can be absent/partial; future certified publication must check full derived input/output and index completeness before changing production mode. Missing an index today can make a draft query omit a row, which is exactly why these APIs must remain drafts until that certification exists.

## Remaining integration constraints

This unit is useful but does not implement the full selected cutover. No mode/private/view/queue atomic publication, complete resumable compiler/catch-up, active view pointer, UI windows, on-demand public hydration or replacement of full legacy arrays is claimed. Three-head retirement orchestration and normal scope view cleanup are still future work.

Preserve chronological zero-facet history when point edits are wired to the queue: raw draft writes currently remove mask0 rows, which is fine for final compiled output. Incremental user edits must not blindly use `current=nil` after final-facet removal when earlier unobserved base/pending history should retain createdAt/folder semantics. Recompute one target's exact relevant history or retain the required intermediate state; avoid a hidden full-library replay.

Installed/backend-first rollout, real SDK/auth, cross-device/physical-device, large pending/positions/server export throughput and actual recoverable iOS save failure remain open. Fix the three concrete boundary issues and rerun current-tree focused/full evidence before accepting the component; do not enable production mode from this review.
