# Independent A2 large-folder cross-judge

Both candidates are design sketches, not implemented behavior. I read both in full and checked the current `librarySync.ts`, `library.ts`, schema, native folder callers, and the receipt-stream decision. Scores are 1–5 under the frame rubric.

| Criterion | A: manifest job | B: cohorts |
| --- | ---: | ---: |
| Exact delete/undo/concurrent move semantics | 3 | 4 |
| Bounded work and payload at arbitrary size/history | 2 | 4 |
| Restart, retry, ACK and ownership clarity | 4 | 3 |
| Small deep interface and complete caller migration | 3 | 2 |
| Red/green proof and migration path | 3 | 2 |

**Recommend A as the smallest viable base, subject to the corrections below.** It keeps `savedItems.folderId` authoritative and fits the existing frozen-frame/receipt stream without migrating every membership to a new table. A complete, indexed manifest plus a constant-size visibility flip can express exactly which members the server deleted, and an offline Undo can name the deletion operation. Its per-member fact cost is real, but bounded chunks make that cost observable and testable. B's cohort model is a stronger O(1) ordinary-delete design and gives a clearer bound on repeated member fanout; its second authoritative membership representation, page-based native snapshot migration, alias normalization, and legacy API transition are a much larger A2 cutover.

**A is not safe to implement verbatim.** During restore it records a member's disposition, then proposes a later final visibility flip. A move/removal after that disposition would make its final counts stale unless every member writer updates or invalidates the fact, or read/materialization checks the live membership version. The old-ID alias must never make a superseded member appear restored. A also leaves current `readSavedSnapshot`/`savedSnapshot` and export as whole-account `.collect()` calls; changing delete to pages while keeping those reads makes arbitrary member count still unbounded. Add bounded item/folder pages and a native page-assembly contract before claiming arbitrary-size support. The delete scanner's folder epoch is sound only after **all** write paths—including legacy `library.ts`, guest merge, restoration, and old installed clients—bump it transactionally. A's job status must distinguish durable start from terminal applied/superseded outcome; ACK of “started” cannot be presented as completed deletion. The per-deletion fact table can grow as members × deletion history: specify when facts remain needed for offline Undo, when they may be compacted, and an explicit storage/admission policy. Workers must recheck owner existence after account erasure.

**B is not a small alternative.** It correctly avoids unbounded member scans for ordinary delete and caps alias resolution to one hop, but `savedItems.folderId` is currently read and written throughout the app and backend. The proposed separate Membership table plus dual-read/dual-write migration is an ownership change, not just a folder operation change. Cohort normalization is paged, yet a folder with arbitrarily many historical cohorts can leave later structural operations queued for arbitrarily long; this is bounded per call but not bounded completion time. The sketch needs a precise terminal outcome for a queued delete/restore if an intervening move or erasure changes its premise. A “pending” receipt must remain unacknowledged under the existing exact receipt stream, or use a separate explicit accepted-versus-completed contract; it cannot be compacted as success. B does identify the necessary paginated read/export migration and old-client incompatibility more honestly than A; carry those requirements into A. Neither design can keep the legacy synchronous full member arrays at arbitrary size, so version that contract or return a truthful bounded incompatibility result while retaining recovery data.

**First verifiable unit:** write a red backend fixture with 501 and a larger synthetic member set against the current `folder_too_large` path. It should interleave a newer move, removal, same-name folder recreation and offline Undo; capture only server-observed membership, assert no partial visible state, and count documents touched/bytes returned per step. Then implement A's server-side job/fact/epoch core for that fixture, including one bounded Saved read page and every membership writer's epoch update. Keep the existing frozen-frame receipt/ACK replay and account-bound worker checks in the fixture. Migrate iOS and Android folder commands/projections together in the next verifiable unit, followed by old-client/migration and native real-store restart tests. Local green fixtures do not close the still-open authenticated iOS↔Android gate.
