# Native committed-manifest adoption recheck

**Verdict: the new central guard closes the observed unknown-cursor ACK bypass as a temporary fail-closed measure.** Both `LibraryPartitionState.checkCursor` implementations reject either `folder_deleted_manifest` or `folder_restored_manifest` anywhere in an outstanding committed receipt before `adopt` can clear `frozen`, advance `nextSequence`, or create `acknowledgement`. The red logs demonstrate the prior failure: reconciliation/retirement/poll/ACK-cursor adoption could create an ACK intent without collecting the manifest. I inspected the new source and tests; I did not rerun a green test or certify the future outcome collector.

The guard covers all cursor adoption entry points: `settle(.reconcile)`, `settlePending(.reconcile)`, `settleRetirement`, and `settleAcknowledgement`. `settlePending(.accepted)` has two branches: a matching frozen original goes through direct `settle(.accepted)`; an unknown or forked original builds a committed cursor and reaches `adopt`. Direct `settle(.accepted)` rejects manifest outcomes in `settleReceipts` before changing persisted fields. On both platforms, `settleReceipts` accumulates recovery/recent rows locally and writes them to state only after checking all receipts, so a manifest later in a mixed reply cannot partially settle earlier receipts. `pollRequest` checks only a pending cursor and creates no ACK.

The focused iOS/Android tests each loop over both manifest kinds and exercise four important routes: frozen-frame reconcile, invalid-frame retirement, accepted poll after a different-command pending fork, and ACK reply carrying the next committed cursor. The state equality assertions matter: in the first two routes the original frozen change remains intact; in the fork route the prior pending adoption has already moved the original into historical recovery, and the rejected terminal response leaves it there; in the ACK route the existing nonmanifest ACK intent remains unchanged. The test does **not** directly exercise `settlePending(.reconcile)` or a direct mixed receipt with a manifest after another outcome. Both reach the same guard/staging code, but add explicit fixtures when changing this area again.

Limits of the claim:

- A cursor whose `closedThrough` has already advanced past an old manifest and has no committed slot cannot reveal that history to this guard. Adopting that cursor can retain a frozen original as historical recovery, but it does not create a manifest ACK. This fix cannot reconstruct missing server proof or member details.
- Rejecting an outstanding manifest leaves the stream unable to advance on these clients. That is appropriate while the collector and public producer are gated; it is a visible retry/failure condition, not successful large-folder sync. The eventual collector must durably bind and preserve needed outcome details before replacing this rejection with settlement.
- Store-level owner checks and captured session generation still guard real callbacks; `LibraryPartitionState` tests alone do not exercise Clerk token dispatch, cross-account delivery, or process restart. The red logs are pre-fix failures, not post-fix pass evidence.

No alternate ACK path emerged in the reviewed native partition methods. Keep the guard until the verified page collector owns **every** direct and adopted manifest path; do not remove it merely because the server page query exists.
