# Held-frame lifecycle review

Read-only source review of the uncommitted held-frame core, October 19. Tests were building; no pass status is inferred. The public folder producer, success commit and native cutover are disabled, so this report addresses the held protocol only.

## Blocking finding

**P1 — A pending proof can retain and later confirm the wrong local frozen intent.** Both native `adopt(cursor)` implementations keep the original frozen frame when pending `sequence` and `batchId` match, without comparing pending `digest` to the digest of that frozen batch (`ios/Hadithly/Core/GuestData/GuestMergePlanner.swift:484-494`; `android/app/src/main/kotlin/com/hadithly/app/core/data/LibrarySync.kt:208-218`). `settlePending(.accepted)` then checks the committed digest against the *server pending proof* and, if the local batch ID matches, calls ordinary `settle` on that local frozen batch; ordinary `settle` checks IDs/revisions but not the committed digest against local commands (`GuestMergePlanner.swift:497-545`; Android `LibrarySync.kt:220-269`). A restored same-installation fork can have the same sequence/batch ID and operation IDs/revisions but changed folder target/content. The server correctly returns `reconcile` for its different batch digest (`backend/convex/lib/librarySyncFrames.ts:11-21`), yet the client keeps its mismatching frozen original, polls the server pending proof, and can mark its different original as accepted when terminal receipts arrive. Keep the original only on exact batch digest equality; otherwise archive it as historical recovery and ACK only the server proof. Test a clone with same batch/operation IDs and revisions but different command value/target through pending → terminal poll on both platforms.

## Confirmed boundaries

- The pending slot is owner+installation scoped, stores one bounded original batch server-side, and carries only metadata in cursors (`librarySyncFrames.ts:6-49`; `backend/convex/lib/librarySyncPolicy.ts:62-76`). `holdFolderFrame` verifies owner, exact operation ID/time, manifest generation, original folder, epoch and expiry before binding. There is no simultaneous pending and committed slot.
- `applyBatch` returns the exact existing pending/committed proof or a no-effect reconcile, while `pollPending` derives owner from JWT and checks the requested sequence, batch, digest, manifest and generation (`backend/convex/librarySync.ts:239-277`). ACK closes only a committed slot; invalid-frame retirement cannot close a pending sequence (`librarySync.ts:292-334`). The existing sparse future fences remain separate.
- Manifest abandonment/expiry calls `failHeldFolderFrame` before fact cleanup. That function conditionally turns a still-matching pending slot into a terminal conflict receipt in the same mutation, preserving the original batch receipt identity (`backend/convex/lib/savedFolderManifests.ts:55-59,99-110`; `librarySyncFrames.ts:51-65`). Owner erasure prevents worker recreation. Native waiting metadata is persisted in the owner partition; missing partitions are not recreated by response settlement (`ios/Hadithly/Core/GuestData/GuestDataStore.swift:392-426`; Android `GuestStore.kt` owner-partition settlement methods).

The present tests cannot establish a successful large-folder delete or Undo: no producer/final success publisher is enabled. An exact-digest clone test is needed before this held protocol is used. Existing installed-schema and real auth/device gates remain open.
