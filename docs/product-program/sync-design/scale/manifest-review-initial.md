# Folder manifest preparation review

Read-only review of the uncommitted preparation core, October 19. Tests were running. This review does not certify logical deletion, native API cutover, or >500-folder support.

## Finding

**P2, blocking before cutover — Retrying an abandoned operation returns a live-looking handle.** `prepareFolderManifest` finds an existing `(owner, operationId)` row and returns `{ kind: "manifest", id, generation }` for every state after matching folder/time (`backend/convex/lib/savedFolderManifests.ts:18-25`). A page that detects an epoch change, missing folder or expiry sets state `abandoned` and stops scheduling scan work (`:45-48,52-63`). Cleanup may remove its facts but deliberately retain the abandoned header until the lease expires (`:88-103`). A retry of the same immutable operation during that interval therefore reports a manifest even though it cannot reach `prepared`; the current test codifies the same return after a changed scan (`backend/convex/savedFolderManifests.test.ts:66-80`). Return the terminal conflict reason for `abandoned`/`purging`, or expose that terminal state in a bounded owner-scoped status contract before wiring the frozen frame. Do not silently restart it with the same operation ID after cleanup.

## Source checks

- One page reads at most 50 owner+folder members with an explicit byte cap; it writes only IDs, item IDs, membership times and ordinals, not notes/provider text (`savedFolderManifests.ts:64-73`; `schema.ts:549-568`). Facts, count, cursor and next scheduled step commit in one mutation. Generation and exact expected step reject duplicate/late workers (`savedFolderManifests.ts:52-55`). A concurrent accepted membership change touches the captured folder epoch; missing folder or changed epoch/time abandons without visible Saved changes (`savedMembership.ts:8-22`; `savedFolderManifests.ts:61-63`). Prepared fact reads recheck owner, generation, expiry and the current folder guard (`:76-85`).
- Initial preparation bounds active work to one scanning/prepared header per folder and four per owner, not a member count; exact operation-ID reuse with different folder/time throws (`savedFolderManifests.ts:21-42`). A same-name replacement has a new folder ID and cannot satisfy the captured identity. Owner erasure prevents late page progress and schedules bounded fact/header cleanup (`:55-57,399-415`; `backend/convex/users.ts:430-432`).
- The revised expiry sweep uses indexed `.take(25)`, moves each selected header to `purging` with a future retry deadline in the same transaction, then schedules cleanup; this avoids cursor skipping when earlier headers are deleted (`backend/convex/librarySync.ts:384-395`). Fact purge deletes at most 50 per step and retains a discoverable header until facts are gone (`savedFolderManifests.ts:88-103`). A canceled scheduled scan is retried by the five-minute stale-header worker without renewing its inactivity lease (`librarySync.ts:368-382`; `crons.ts:52-54`).

The >500 delete probe remains an explicit red/open gate; a prepared header is neither a deletion receipt nor an ACK-able success. Hosted read/transaction limits, installed-schema migration and final logical delete/Undo semantics still require later proof.
