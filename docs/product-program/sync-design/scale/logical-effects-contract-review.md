# Logical folder effects contract review

Read-only architect review, October 20. `docs/product-program/sync-design/scale/logical-effects.md` is a proposal; the current checkout still has manifest preparation and held-frame failure only (`backend/convex/lib/savedFolderManifests.ts`, `lib/librarySyncFrames.ts`). No tests or deployment were run, and this is not a >500-support verdict.

## Contract blockers before implementation

1. **P1 — Expiry can race a staged Undo unless its handle is reserved at Undo start.** The contract gives facts a 30-day deadline from logical deletion and says unconsumed expiry materializes orphan clocks and removes tombstone/facts, while only *already-restored* handles are explicitly protected (`logical-effects.md:31-36`). A restore can begin at day 29.9, stage some members in bounded pages, then hit day 30 before its final visibility commit. If expiry still sees an “unconsumed” handle, it can purge the facts those stages reference and produce an unavailable result for work already accepted. Reserve/lease the deletion handle transactionally when the restore job starts; expiry must treat `restoring` as active, either complete it or publish a terminal conflict before bounded cleanup. Test expiry between stage pages and between final stage and visibility flip. Today's prepared-header purge already removes facts after expiry in 50-row steps (`savedFolderManifests.ts:98-115`), so the future phase rules must override that behavior for retained delete/restore handles.

2. **P1 — One deletion authority needs a single restore owner before staging.** Each member has only one staged slot keyed to a restore operation (`logical-effects.md:10-15`), but the contract says only that a *consumed* handle cannot reactivate after a later delete (`:25-29`). Two offline/clone Undo operations with different IDs can target the same retained deletion before either reaches final commit. Without a header-level compare-and-set reservation, both can stage/count the same facts, overwrite a member slot, or publish incompatible receipts. Set `restoreOperationId` on the deletion handle at first accepted Undo; same ID is idempotent, different ID returns a bounded conflict. Release that reservation only through an explicit terminal transition, never via a worker timeout that could leave staged slots.

## Invariants to encode and prove

- The physical raw pointer can remain at clock 50 after logical delete at 100. Every writer/read must use an effective no-folder value and a clock floor of 100; a delayed move/removal at 75 cannot consume Undo eligibility (`logical-effects.md:3-8`). A move at 125 **during staging** may be accepted and must clear that member's stage and update final counters; after final restore visibility at 150, a delayed 125 must lose to the restored mark. Test these two orderings separately rather than treating a stage as already visible.
- The final delete transaction must check exact owner, original folder ID, captured epoch and metadata time, then atomically remove the folder, write the tombstone and publish only a **bounded terminal receipt**. Preparation or a pending held frame cannot be ACKed as deletion success (`logical-effects.md:3-8,38-43`; `librarySyncFrames.ts:24-49`). Existing `folder_deleted`/`folder_restored` native receipt arrays are not ready for a manifest outcome collector, so the public producer must stay disabled until detail pagination and durable native collection exist.
- A same-name existing destination must be locked against both sync and legacy structural deletion throughout staging and finalization; a destination created at final flip must use the owner+normalized-name unique lookup in the same transaction (`logical-effects.md:17-23`; current legacy `library.ts:776-827`). Stage counters need owner/generation/step CAS and per-member disposition changes in the same transaction as accepted concurrent writes. Final totals must freeze and remain historical after later edits.
- Retention cleanup must not delete a tombstone while any orphan pointer still lacks the deletion clock, nor delete a restored handle before bounded materialization is complete. The “at most four identities per step” claim (`logical-effects.md:45-48`) needs execution evidence with large note documents, a real 501/2,001-member run, interruption/retry, foreign owner rows, and export/read projections.

The current preparer has no logical delete or restore producer, so the two findings are contract gaps to close before code cutover, not defects already shipped to users.
