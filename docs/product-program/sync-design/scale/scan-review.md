# Folder scan prerequisite review

Read-only source review of the uncommitted membership-epoch/index delta from `5dcc4dc`, October 19. Tests were running. This is not a large-folder job cutover or A2 completion review.

**Verdict: no blocker found in the new scan guard and epoch prerequisite.** `savedFolderScanGuard` uses the `[userId, folderId, folderUpdatedAt]` index and reads only its descending first row; the result is an owner-scoped current maximum, not a 500-row prefix estimate (`backend/convex/lib/savedMembership.ts:17-22`; `schema.ts:562-581`). Missing installed `membershipEpoch` reads as zero, and every accepted change to an active folder increments the same folder row in the mutation (`savedMembership.ts:8-15,50-63`). This covers dated moves out/in, a newer timestamp on the same folder, and an unversioned claim of previously unset membership. Older/equal same-value observations do not touch it. Deleting a Saved row after its last facet now touches its current folder before removal (`savedMembership.ts:24-28`; `library.ts:627-701`; `librarySync.ts:148-231`). Both native/legacy folder restore paths touch the destination for each actually restored member (`librarySync.ts:105-118`; `library.ts:807-827`). Guest V2 placement routes through the helper (`guestMerge.ts:240-265`). Note-only edits do not invalidate membership scan, which is the correct domain split.

**P2 — The current physical delete cap still counts foreign pointers.** `librarySync:folder_delete` reads `savedItems.by_folder.take(501)` and checks `members.length > 500` before filtering `member.userId !== userId` (`backend/convex/librarySync.ts:72-86`). The new indexed scan guard correctly excludes a corrupt foreign row that points to this folder (`savedMembership.ts:18-21`; `savedFolderScan.test.ts:50-62`), but the physical delete can still report `folder_too_large` for 500 owned members plus one foreign pointer. Normal public placement writes reject foreign folders, so this requires existing malformed data; it is not a new bypass and does not invalidate the scan epoch. The bounded job cutover should page by owner+folder and avoid using the old global `by_folder` count as its admission rule.

The folder itself remains JWT-owner checked before the guard; `touchSavedFolderMemberships` only patches folder rows whose `userId` matches the item owner (`librarySync.ts:72-74`; `savedMembership.ts:9-14`). Existing physical delete paths remove the folder row in the same transaction, so a future prepared job that rereads the folder will fail closed if one deletes it during scanning. Same-name restore creates or reuses a new owner-scoped folder row and begins at its own zero epoch; accepted member restoration then increments it. The present code still has the explicit >500 outcome, and tests must finish before treating this prerequisite as verified.
