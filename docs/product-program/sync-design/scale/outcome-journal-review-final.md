# Native outcome journal re-review

Read-only review of the revised October 20 Swift and Android source. **The earlier routine whole-manifest scans, post-erasure scope metadata, Android pre-owner scope creation, and conflicting-unavailable replay gaps are repaired in the inspected code.** I did not run tests; the parent is running the focused native suites. This is a journal-core verdict only: coordinator/ACK, export, pruning, whole-partition scale, public producer and live account/device gates remain open.

The new verification continuation is coherent. A final page commits `checkpoint.counts == expected` and moves to `verifying(0)`, without claiming complete. Each subsequent step reads exactly the next `min(50, remaining)` ordinals, checks the decoded row against persisted ordinal/identity/disposition columns, adds category counts, and saves the continuation with the header. On crash before that save, the same rows are checked again; after save, the next ordinal is used. Completion requires the verified category counts to equal the immutable receipt totals. Swift's padded `ordinalKey` range and Android's `(collection_key, ordinal)` primary key make page selection bounded; evidence reads validate one bounded contiguous page. A duplicate page compares existing rows without rewriting them. Neither implementation scans all prior rows on each collection step anymore. The terminal verifier trusts the previously saved `complete` state on later reopen rather than re-reading every row; that is consistent with atomic row/header transactions and the erasure-generation fence, but should be described as trust in a completed durable verification, not a fresh full audit on every reopen.

Erasure ordering is substantially better. Account deletion retains its deletion intent while the journal rotates scope generations and deletes members, headers and scopes; interruption before phase advance can rerun the sweep. Swift uses repeated 50-row saves, Android repeated committed 50-row SQL deletes, so a stale fetched page cannot commit after the generation changes. Android now validates the active owner/deletion phase before creating a scope, under the same store mutex; this closes the metadata resurrection case. The final scope delete removes subject/owner metadata after evidence is gone. Both duplicate/unavailable paths now accept only the same terminal unavailable reason at the same ordinal; a conflicting old-start unavailable result cannot masquerade as a replay.

**Remaining boundaries to make explicit before cutover:**

- `eraseSyncPartition` remains a two-store operation on both platforms: journal erase commits before partition removal. A crash in that gap leaves the partition intact and later collection can create a fresh journal for the same proof. This is safe against orphan disclosure but is not a final erasure guarantee. Keep this method as a test/reset helper or give production callers a durable erase intent; account deletion already has that intent. Add a crash/reopen fixture at this exact gap if it will be used outside tests.
- `outcomeEvidencePage.done` means the end of the **locally collected prefix**. It can be true while the checkpoint is `collecting`, `verifying` or `unavailable`; it does not certify that the server's manifest is complete. Future export/recovery code must report `checkpoint.status` and expected totals, never infer completeness from `done` alone. A `proof_unavailable` checkpoint likewise cannot authorize ACK.
- A `complete` header can be handed out after prior terminal verification without rechecking rows; this relies on no post-completion row mutation except fenced erasure. Keep that invariant private to the journal and test reopening at every verifier save boundary, including zero and exact-50 totals. The new real-store fixtures should also inject count/category and stored-row metadata corruption, erasure interruption, repeated same/unavailable replies, and duplicate rows across reopened contexts. Old installed SwiftData schema migration and actual index-backed query cost still need direct evidence.

The journal does not currently mutate the large native partition for each page, and it still creates no ACK intent. Keep the manifest guards until settlement explicitly binds the exact frozen operation to this verified journal and durably preserves any partial/unavailable original.
