# Membership boundary review

Read-only review of the uncommitted diff from `b198c18`, October 19. The three red tests in `/tmp/hadithly-membership-clock-red.log` establish the prior failures; replacement tests were still running. This is not a large-folder-job or full A2 review.

## Finding

**P1 — Guest merge still treats a later note edit as a later folder move.** `writeSavedMembership` correctly compares a proposed placement clock with the current `folderUpdatedAt` and causal mark (`backend/convex/lib/savedMembership.ts:18-33`). But `guestMerge` supplies `incoming.updatedAt` as that proposed *membership* clock (`backend/convex/guestMerge.ts:229-233`). Both native V2 planners build `SavedItem.updatedAt` as the maximum bookmark/favorite/note time, then attach only `folderLocalId`, discarding the separate guest membership `updatedAt` (`ios/Hadithly/Core/GuestData/GuestMergePlanner.swift:129-144,178-180`; `android/app/src/main/kotlin/com/hadithly/app/core/data/GuestStore.kt:464-479`). Example: guest folder choice at 1,000, guest note edit at 5,000, other-device folder move at 3,000. V2 sends aggregate `updatedAt=5,000`; the helper accepts the stale folder choice as newer and overwrites the other device. The new tests vary only the aggregate item timestamp as though it were the folder timestamp (`backend/convex/librarySync.test.ts:433-473`), so they do not expose this sequence. Carry the membership's own clock in the V2 payload and use it for placement; an old payload without that clock cannot safely claim to outrank an existing cloud placement. Test a later note edit with an older folder intent.

## Source checks

- `decideMembershipWrite` returns unchanged for the same destination at an older/equal clock and does not replace the deletion mark; different equal-time values tie in favor of cloud (`savedMembership.ts:8-15,26-33`). That directly addresses the no-folder Undo regression without treating observation as a new write.
- The helper rejects a foreign folder before patching, and all three callers obtain the item under the JWT-derived owner. `librarySync` resolves local/server folder references against that owner; the legacy assignment validates the target folder; guest merge maps request-local IDs to this owner's folders (`savedMembership.ts:21-25`; `backend/convex/librarySync.ts:42-47,149-164`; `backend/convex/library.ts:764-784`; `guestMerge.ts:93-107,220-233`).
- On accepted placement the helper updates `folderId`, `folderUpdatedAt`, overall `updatedAt` by `max`, and the causal mark in one mutation (`savedMembership.ts:27-33`). Guest merge's later facet patch also uses a max for overall `updatedAt` (`guestMerge.ts:242-252`); it no longer rewinds the folder clock. `membership_put` is counted in its batch's Saved version, and legacy assignment advances that version on a real write (`librarySync.ts:240-261`; `library.ts:775-784`).
- The five-minute future-clock guard is at the shared boundary (`savedMembership.ts:23`). It is compatible with normal current timestamps, but a legacy V2 payload with a badly skewed aggregate `updatedAt` now fails the whole merge transaction and retains local data; native/recovery messaging still needs verification. The red invalid-clock cases assert rollback, not successful old-client migration (`librarySync.test.ts:502-509`).
