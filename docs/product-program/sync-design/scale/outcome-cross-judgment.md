# Outcome collection cross-judgment

**Recommend A's row journal as the base**, with B's explicit erasure fence, proof-unavailable distinction, and Undo-aware pruning. Neither candidate is implementation-ready verbatim. The current server returns at most 50 manifest members per page, but the native stores still reject both manifest outcomes; this judgment is about the next cutover, not a claim that large-folder sync works now (`libraryOutcomePages.ts`; Swift `GuestMergePlanner.swift:465-546`; Android `LibrarySync.kt:222-247`).

| Rubric (1–5) | A: SwiftData/SQLite rows | B: page files |
| --- | ---: | ---: |
| Exact page/receipt/owner binding and replay | 4 | 4 |
| Bounded persistence and crash consistency | 4 | 3 |
| Partial recovery, export and erasure | 3 | 4 |
| Deep interface and honest Saved projection | 4 | 2 |
| Real-store proof and migration limits | 3 | 3 |

A concentrates page validation and durable collection behind `OutcomeJournal.collect → VerifiedCheckpoint`; the existing coordinator need only settle a verified compact result, then follow its ACK branch. SwiftData rows fit the current iOS store, and SQLite gives Android atomic row+header page commits while keeping the existing AtomicFile JSON partition small. The Android cross-store order is essential: **journal complete → compact partition settlement/ACK intent → server ACK**. On reopen, a complete journal with stale JSON may reattempt exact settlement; a JSON ACK intent with missing/conflicting journal must fail closed. B also explains an ordered protocol, but exposes `open → persistPage → settle` to the coordinator and adds temp-file naming, exclusive creation, file and directory synchronization, checkpoint reconstruction, conflict files and orphan walks. That is temporal decomposition unless one journal method owns it all. B's “rename create-if-absent” guarantee needs platform-specific proof; ordinary rename must not silently replace a conflicting page.

**Required corrections/grafts for A:**

- Bind the header and every page to the captured subject, namespace, server owner, installation/client key, sequence, batch/digest, exact receipt ID/revision, manifest ID/generation and phase. Validate the server's echoed request and contiguous ordinal/category totals before writing. The current producer enforces 50 rows but does not visibly enforce the promised 64 KiB encoded page cap; add and test that boundary. An identical duplicate may resume; a different row or endpoint for the same ordinal quarantines the collection and preserves originals. Never attach a same-operation-ID/different-command fork to the old header.
- **Prove database uniqueness, not just an application lookup.** Use immutable synthetic row keys for ordinal and member identity plus strict fetch-and-compare before insertion. On iOS, `@Attribute(.unique)` is available, but SwiftData documents collision upsert behavior; a conflicting save must never overwrite the prior fact ([Apple WWDC24 SwiftData](https://developer.apple.com/videos/play/wwdc2024/10137/)). Test duplicate/conflicting pages across reopened contexts and schema migration on the app's iOS 17 target. On Android use SQLite `UNIQUE` keys with insert-or-reject/compare, never `REPLACE`; test process restart and a failed transaction between row insert and header advance.
- Separate `proof_unavailable` from `detail_unavailable`. In current `readLibraryOutcomePage`, `proof_unavailable` means the matching committed stream receipt cannot be established; **no ACK or success settlement follows**. `detail_unavailable` may follow a verified receipt when the manifest expired; persist the exact proof, partial rows, reason and locally available source. ACK that case only if the protocol explicitly defines unavailable as a terminal recoverable result. A's single “unavailable ready” path is too broad. A short page, network failure or missing row is never completion.
- B's subject+namespace erasure generation belongs in the row journal too. Current iOS deletion scans partition rows, and Android deletes JSON partitions; neither discovers new orphan journal rows after the partition is gone. Deletion must fence active writers before sweeping headers, members and temp/recovery records, persist its fence through restart, and prevent a late collector from recreating rows. Export must discover evidence by captured subject+namespace, stream it with a prune/erase fence, and fail explicitly if required rows vanish during export; the current `portableState` includes only the JSON partition.
- Do not prune successful **delete** facts merely because ACK and an owner-tagged Saved revision have arrived. An unexpired Undo, frozen/offline restore, or retained recovery reference may still need the original identity set. Prune only after ACK, authoritative revision, and absence of those dependencies; retain partial/unavailable/conflicting evidence and available originals for private recovery/export. A compact header can then outlive deleted successful rows only while needed. No collected subset becomes a claimed complete set.

**Projection and first proof unit.** Both candidates correctly avoid loading member pages into `LibraryProjection`. Until a complete terminal result and the authoritative Saved revision, show a pending transition without guessed restored members; when a snapshot at or beyond the committed Saved revision arrives, its membership wins and confirmed overlay pruning may run. The existing `pruneConfirmed` version check is the seam, but current native projection still consumes old `folderRestored.restored` arrays and must be migrated on both apps. First implement a backend exact-page fixture for 0/1/50/51 and mixed restore categories, then real iOS SwiftData and Android SQLite+AtomicFile crash/reopen tests: lost page response; identical/conflicting duplicate; failure before and after page commit, terminal header, JSON settlement and ACK; proof unavailable before ACK; old Undo after revision; erased partition with orphan journal rows; export during prune. Assert row/page bytes and no member arrays in either partition blob. Old installed schema, whole-file Saved cache, public producer, export/read cutover, hosted limits and authenticated cross-device gates remain open until those paths run end to end.
