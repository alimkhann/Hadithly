# A2 core review

Requested reviewer model: gpt-6-sol (parent invocation metadata). Read-only source review of the new sync core; no cloud or native build run.

## Blocking findings

1. **P1 — An old folder delete can erase a newer cloud move.** `backend/convex/librarySync.ts:76-91` deletes every current member of the folder and the folder itself without comparing the delete operation's timestamp to the folder or membership marks. In fact it sets each membership time to `max(operation.at, member.folderUpdatedAt)`, then stamps the old deletion as the cause. If device B moves a Saved item into the folder after device A's offline delete was made, A's later sync removes B's newer placement. This contradicts the newer-cloud guard used for `membership_put` at `:148-154`. Return `superseded`/conflict for an old delete or define a versioned delete rule that cannot silently consume newer membership; test two-device ordering through `applyBatch`.

2. **P1 — Folder restore receipts overstate preservation.** `backend/convex/librarySync.ts:93-110` creates/reuses a folder, then silently skips each requested member if its item is absent, currently assigned elsewhere, or its mark no longer names the deletion. It always returns `{ kind: "folder", folderId }`. Both local `settle` implementations treat that outcome as accepted and discard the frozen change (`ios/Hadithly/Core/GuestData/GuestMergePlanner.swift:311-333`; `android/.../core/data/LibrarySync.kt:86-112`). Thus a partial restore loses its unrecovered membership intent without a conflict/recovery record. Split membership receipts from folder creation or return a partial/conflict outcome with the skipped IDs; add a mixed-success restore test.

## Targeted core risks to prove before integration

- **Cancellation at Android guest claim:** `LibrarySync.kt:227-237` checks the session, then calls suspending `GuestDataStore.claimGuestForSync`; its `writeLocked` computes the owner-partition move and awaits IO under the mutex (`GuestStore.kt:183-195,316-337`). A session change during that await is checked only after send/settle. A cancelled write may already have committed the guest-to-old-owner move, leaving those drafts unavailable in guest mode until that account resumes. The source does not prove that this loses data or attributes it to B; add a controlled pause at the storage commit and a sign-out/account-switch test before treating cancellation as safe.
- **Notification and retry:** Guest edits notify the coordinator only after successful local saves (`GuestDataStore.swift:414-416`; Android `GuestStore.kt:188-195`), which is the right trigger. Both coordinators resnapshot after a wake and persist frozen batches before send. Tests currently cover one paused send, restart receipt checks, and mismatch rejection; they do not establish the sign-out-during-claim boundary above or permanent-error classification. Keep those as core test gates, separate from the known unfinished sign-in caller migration.

The reviewed server binding is JWT-owner checked (`backend/convex/librarySync.ts:16-39,219-226`), receipts are stable on batch replay (`:228-254`), and client receipt matching checks batch ID, operation IDs, revisions, and count before settlement. The 10,000-batch lifetime cap, old `clearAll` callers, unported signed-in projections, folder >500, vanished anchors, deployment, and real account/device proof are already identified open gates; this report does not treat their existence as a newly found defect.

## Addendum — October 18 core fixes

The two P1 findings above are **fixed in the current source**. Folder deletion now refuses to remove the folder if its own or any member's timestamp is newer than the delete (`backend/convex/librarySync.ts:76-94`); the backend test exercises a newer cloud placement (`librarySync.test.ts:121-140`). Folder restore now reports `restored`, `superseded`, and `missing` IDs separately (`librarySync.ts:96-115`), and both native settlement paths retain partial results in recovery (`ios/Hadithly/Core/GuestData/GuestMergePlanner.swift:311-335`; `android/app/src/main/kotlin/com/hadithly/app/core/data/LibrarySync.kt:86-112`). The mixed restore test verifies the newer destination survives (`librarySync.test.ts:142-164`). Backend 377/377 and the reported native core tests pass; I did not rerun native builds.

The new `LibraryWriteContext` captures owner, session and generation before async writes, then verifies all three at enqueue (`GuestMergePlanner.swift:348-352,431-440`; `LibrarySync.kt:126-129,208-221`). Both stores now require an existing owner partition when enqueuing (`GuestDataStore.swift:380-384`; `GuestStore.kt:350-355`), so a stale enqueue cannot silently recreate an erased partition. I found no new concrete blocker in those changes. The Android sign-out-during-suspended-claim test remains a focused proof gap from the earlier review, and strict corrupted-store reads were still being repaired during this pass. These are core review limits, not evidence of completed sign-in or signed-in-write integration.

## Final Android storage addendum — October 18

The damaged-file path now fails closed: `GuestStore.kt:174-178` throws `StoreUnavailable` rather than returning an empty `GuestStoreFile`; writes call that read under the mutex before producing an atomic replacement (`:180-193`). This preserves the damaged file for recovery. Guest `UserLibraryModel` reads and writes now pass through `launchGuestOperation`, which propagates coroutine cancellation and sets the existing `LoadState.Failed` on storage errors (`UserLibraryModel.kt:174-176,440-450`). The old sign-in caller catches snapshot-read failure, shows the localized Saved load error, and returns without merging or clearing (`SessionManager.kt:123-133`). The instrumentation cases cover corrupt-file retention, read/write failure display, and legacy JSON claim/reopen (`GuestMergeRaceTest.kt:138-176`). I found no new concrete regression in these edits.

`LibrarySync.kt:240-250` now rechecks session immediately after the suspending claim, so it will not freeze or send after a changed session. The earlier **suspended-commit cancellation gate remains open**: the claim may commit into the captured owner's durable partition before that check, and the current tests do not pause at the atomic write to prove the sign-out boundary. The core is still dormant relative to the old `clearAll` sign-in path and signed-in write/projection migration; this addendum makes no A2 completion claim. The parent's final Android rerun was in progress during this review.
